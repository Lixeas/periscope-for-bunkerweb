# Kubernetes compatibility — design (ROADMAP v0.3.0, goal 2)

## Intent

Today Periscope is deployed with Docker Compose. Two situations call for Kubernetes: running the
**console** in a cluster, and running an **agent** inside a customer's cluster next to a BunkerWeb that is
itself deployed on Kubernetes. The user (project owner) has no Kubernetes experience and relies entirely on
the designer's recommendations, with one requirement: the result must be flexible and *cloud native*, i.e.
configured declaratively, secrets and storage handled the Kubernetes way, no assumption about one cloud,
one ingress controller or one storage class, and as portable as the Compose setup it complements.

The Compose files stay the reference for single-host Docker; nothing in this goal changes them.

## Decisions (all the designer's calls, the user delegated them)

- **Packaging: two Helm charts**, `deploy/helm/periscope` (console) and `deploy/helm/periscope-agent`
  (agent). Helm is the de-facto standard, every knob is a documented value, and a user who does not want
  Helm can run `helm template` to get plain manifests. Two charts because the console and the agents live
  in different clusters with different lifecycles and different secrets.
- **No Operator, no CRD, no bundled PostgreSQL.** External PostgreSQL (goal 6) is the production database;
  recommend an operator such as CloudNativePG in the docs, do not ship one.
- **One console replica, enforced** (not a value). The collector, the agent listener, rate limits and
  lockouts are in-process state. Deployment strategy `Recreate` so two pods never run side by side during
  an upgrade (SQLite and the in-process state would conflict).
- **Secrets are never generated by the chart.** `lookup`-based generation breaks under GitOps tools and
  `helm template`, and a silently regenerated `PERISCOPE_SECRET_KEY` makes every stored credential
  unreadable. The chart requires either `secretKey.existingSecret` (works with External Secrets, Sealed
  Secrets, Vault…) or `secretKey.value` (stored in a Secret created by the chart with
  `helm.sh/resource-policy: keep`), and fails with a clear message otherwise.
- **Kubernetes 1.27 or newer**; nothing cloud-specific.

## Goals

1. Install the console with `helm install` and a short values file; reach the web UI through an Ingress of
   any class (or any other mechanism: the chart only provides a `Service` and an optional `Ingress`).
2. Expose the **agent listener** (mutual TLS) as its own `Service` (type configurable, annotations
   configurable for cloud load balancers). It is never put behind an Ingress that terminates TLS.
3. Install an **agent** in a customer cluster with `helm install`: it enrolls itself (no `kubectl exec`),
   keeps its key and certificates on a persistent volume, and reports to the console.
4. Safe by default: non-root (uid 10001), read-only root filesystem, all capabilities dropped,
   `RuntimeDefault` seccomp, no service account token mounted, resource requests/limits set.
5. Operable: liveness / readiness / startup probes, restart on configuration change, graceful stop.
6. Verified by CI on a real (kind) cluster, not only linted.
7. A beginner-oriented guide, `docs/kubernetes.md`.

## Non-goals / anti-goals

- No high availability / several console replicas (needs the in-process state moved out; future work).
- No autoscaling, PodDisruptionBudget (pointless with one replica), service mesh, NetworkPolicy, Gateway
  API objects in this version (document them as possible follow-ups).
- No automatic discovery of BunkerWeb in the cluster: the agent chart takes the BunkerWeb API URL as a
  required value.
- Anti-goals: a chart that only works on one cloud or ingress controller; a secret ever stored in plain
  values by default or printed in logs/notes; a root container; an upgrade that can lose the encryption
  key or two console pods running at once.

## Console chart (`deploy/helm/periscope`)

Objects: `Deployment` (replicas 1, `Recreate`), `Service` (web, 8000), optional `Ingress`, optional second
`Service` for the agent listener (8443) when `agentListener.enabled`, `PersistentVolumeClaim` (unless an
existing claim or an external database is used), `Secret` (only when `secretKey.value` is given),
`ServiceAccount` (no token automount), `ConfigMap` for non-secret `PERISCOPE_*` settings, `NOTES.txt`.

Values (names are part of the design; defaults in brackets):

- `image.repository` [`ghcr.io/lixeas/periscope-for-bunkerweb`], `image.tag` [chart `appVersion`],
  `image.digest`, `image.pullPolicy`, `imagePullSecrets` (the GHCR package may be private).
- `secretKey.existingSecret` / `secretKey.existingSecretKey` [`secret-key`] / `secretKey.value`.
- `config.origins` (list, required when `cookieSecure`), `config.rpId` (required), `config.cookieSecure`
  [true], `config.pollInterval`, `config.probeInterval`, `config.trustedProxies` [`*`, see below],
  `config.extra` (free `PERISCOPE_*` map), `extraEnv`, `extraEnvFrom`.
- `database.url` / `database.existingSecret` + `database.existingSecretKey` (a URL holds a password, so a
  Secret reference is the normal way). Empty = SQLite on the volume.
- `persistence.enabled` [true], `.size` [1Gi], `.storageClass`, `.accessModes` [`ReadWriteOnce`],
  `.existingClaim`. The chart refuses `persistence.enabled=false` without an external database (it
  would silently lose data on every restart).
- `service.type` [`ClusterIP`], `service.port` [8000], `service.annotations`.
- `ingress.enabled` [false], `ingress.className`, `ingress.annotations`, `ingress.hosts`, `ingress.tls`.
- `agentListener.enabled` [false], `agentListener.publicUrl` (sets `PERISCOPE_AGENT_PUBLIC_URL`; its host
  must be a DNS name or IP that agents can reach and that goes into the listener certificate),
  `agentListener.service.type` [`ClusterIP`], `.port` [8443], `.annotations`, `.loadBalancerSourceRanges`.
- `resources` (modest requests, memory limit), `nodeSelector`, `tolerations`, `affinity`,
  `podAnnotations`, `podLabels`, `serviceAccount.create/name/annotations`, `podSecurityContext`,
  `securityContext` (defaults as in goal 4), `terminationGracePeriodSeconds` [30].
- A `values.schema.json` validates types and the required combinations.

Behaviour:

- Probes: startup `GET /healthz` (generous: migrations run at start), liveness `GET /healthz`, readiness
  `GET /readyz` (new, see below).
- Pod annotations carry a checksum of the ConfigMap so a config change restarts the pod.
- `FORWARDED_ALLOW_IPS` is set from `config.trustedProxies`. Default `*` because the ingress controller's
  address is unknown to the chart; document that other pods in the cluster could then forge
  `X-Forwarded-For` (rate-limit buckets, audit IPs) and that a controller CIDR is the tighter setting.
- Writable paths: `/data` (volume) and `/tmp` (`emptyDir`); everything else read-only.
- `fsGroup` set so the uid 10001 can write the volume.

## Agent chart (`deploy/helm/periscope-agent`)

Objects: `Deployment` (replicas 1, `Recreate`), `PersistentVolumeClaim` (small, holds the agent key,
certificates and console address), `Secret` (only when values carry a password or bundle), `ServiceAccount`
(no token). No `Service`: the agent only makes outbound connections.

- **Self-enrollment.** An `initContainer` runs `periscope agent enroll` with the enrollment bundle (from a
  Secret) **only if the volume holds no certificate yet** (idempotent: `test -f agent.crt || …`). Once
  enrolled, the bundle can be removed from the values; later restarts skip enrollment. An expired or
  already used bundle leaves the pod in `Init:Error`, which is visible and explained in the guide. Re-
  enrolling = new bundle from the console + deleting the volume contents (documented).
- Values: `image.*`, `imagePullSecrets`; `enrollment.bundle` / `enrollment.existingSecret` +
  `.existingSecretKey` (a long single-use secret: Secret reference recommended); `bunkerweb.url`
  (required), `.username` [`periscope`], `.password` / `.existingSecret` + `.existingSecretKey`
  (mounted as a file and passed with `PERISCOPE_AGENT_BW_PASSWORD_FILE`, never in an env var),
  `.verifyTls`, `.probeHost`, `.tlsPort`; `persistence.*` as above; the same scheduling / security /
  resources values as the console chart.
- Probes: `exec` `periscope agent health` for liveness (generous initial delay: healthy only after the
  first accepted report) and for startup; no readiness probe (nothing receives traffic). Documented
  consequence: a console outage restarts the pod.
- The agent image is the console image (same `periscope` entrypoint), same pull settings.

## Application changes

- **`GET /readyz`**: unauthenticated, no data, `SELECT 1` on the database; `200 ok` or `503`. With an
  external database this keeps traffic away while the database is down without restarting the pod
  (`/healthz` stays a pure liveness check that touches nothing).
- No other runtime change is expected: configuration is already environment-driven, logs go to stdout,
  SIGTERM is handled by uvicorn.

## Release, versioning and CI

- `Chart.yaml` `version` and `appVersion` follow the application version. `dev/release.py bump` updates
  both charts; a test fails if they differ from `periscope.__version__`.
- CI gains a **chart job**: `helm lint`, `helm template` over several values sets (minimal SQLite,
  external PostgreSQL, ingress on, agent listener on, existing secret) validated with `kubeconform`, and
  expected-failure cases (no secret key, no persistence without external database).
- CI gains a **kind job**: build the image, create a kind cluster, load the image, `helm install` the
  console (SQLite, generated secret), wait for the rollout, check `/healthz` and `/readyz`, then
  `helm upgrade` and check again. The agent chart is rendered and schema-validated but not run
  end-to-end (enrolling needs a console-issued bundle); this is the accepted ceiling.
- At release (existing `release` job, after the image push) both charts are packaged and pushed as OCI
  artifacts to `ghcr.io/<owner>/charts/`, so users can `helm install oci://…`. Chart tests run before it.

## Documentation

`docs/kubernetes.md`, written for someone new to Kubernetes: what you need installed (`kubectl`, `helm`,
a cluster), the vocabulary in five lines, the minimal values files, a copy-paste way to create the secret
key, installing the console, giving it a URL (Ingress example for a generic class), exposing the agent
listener (LoadBalancer vs NodePort, TLS passthrough, the DNS name in `publicUrl`), installing an agent in a
customer cluster, upgrading, backing up (the secret key and the database), the one-replica rule and why,
troubleshooting by symptom (pod `Pending`, `Init:Error`, `CrashLoopBackOff`, 403 on forms = origins, ...).
README links to it. `ROADMAP.md`, `CHANGELOG.md` updated.

## Constraints and known risks

- **Not validated against a BunkerWeb that really runs on Kubernetes** (its API service name/port, how the
  scheduler lists its pods as nodes). Like the rest of the project's BunkerWeb parsing, this is derived
  from reading the source; the guide says so and tells the user which URL to put in `bunkerweb.url`.
  `normalize.py` is only touched if a gap is found and reproducible.
- Agent listener reachability and TLS passthrough depend on the customer's load balancer; the guide gives
  generic guidance and cloud annotations are left to `service.annotations`.
- `*` as default trusted proxy (above) is a convenience default with a documented cost.

## Facts checked in the repository (from the builder review)

- The image already runs as uid 10001 with a read-only root filesystem in Compose (`read_only`, tmpfs
  `/tmp`, `cap_drop: ALL`); writable paths are `/data` and `/tmp` only. SQLite files and WAL live in `/data`.
- `FORWARDED_ALLOW_IPS` is read by uvicorn itself (the image `CMD` uses `--proxy-headers`); the app has no
  setting of its own. Compose maps `PERISCOPE_TRUSTED_PROXY` to it; the chart does the same from
  `config.trustedProxies`.
- `PERISCOPE_AGENT_BW_PASSWORD_FILE`, `periscope agent health` and `PERISCOPE_DATABASE_URL` (PostgreSQL
  with the psycopg driver in the image) all exist already (goals 3 and 6 are done on this branch).
- `periscope agent enroll` writes `agent.key`, `agent.crt`, `ca.crt` and `console.json` under
  `PERISCOPE_AGENT_DIR` (default `./data/agent`; the chart sets `/data/agent`). `agent.crt` is the marker
  the init container tests. Nothing else is written; the agent also gets an `emptyDir` on `/tmp`.
- Beyond `/readyz`, the only code allowed is small: the version sync in `dev/release.py` and tests.

## Calls made by the designer (to check)

- **Expired or revoked agent certificate.** The init container enrolls when `agent.crt` is missing **or**
  when `enrollment.force=true` (one-off, overwrites the files). Recovery is documented: create a new
  bundle in the console, `helm upgrade` with the new bundle and `enrollment.force=true`, then set it back
  to false. Without that the pod restarts in a loop, which is visible and explained in the guide.
- **Agent listener address.** `agentListener.publicUrl` is required when `agentListener.enabled=true`.
  The guide recommends reserving a DNS name (or static IP) first. A two-step install also works
  (install, read the load balancer address, `helm upgrade` with `publicUrl`): the config checksum
  restarts the pod and the listener certificate is regenerated for the new host, as it is after any
  address change; agents keep working because they pin the CA, not the server certificate.
- **Origins and RP ID.** When `config.origins` is empty and the Ingress is enabled, the chart derives
  `PERISCOPE_ORIGINS` from `ingress.hosts` (`https://` when `ingress.tls` is set, else `http://`) and
  `PERISCOPE_RP_ID` from the first host; explicit values win. Without an Ingress, `origins` and `rpId`
  are required (except when `cookieSecure=false`, for trials such as the kind job).
- **Unreleased builds.** The kind job overrides `image.repository`, `image.tag` and `pullPolicy` with
  `--set`. The chart job also runs `helm package` on pull requests (no publish); only the `release` job
  pushes charts, after the image, when the version tag is new.
